# Commit message and application

- Derive the team convention only from consistent recent commit messages, including any recurring ticket IDs, scope, capitalization, subject length, body, or trailers. Do not use guidance documents or configuration as evidence of the convention. If history is inconsistent or too sparse to establish one, fall back to Conventional Commits. Do not copy ticket IDs or breaking-change markers from unrelated commits.
- Under the Conventional Commits fallback use `<type>[optional scope][!]: <description>`. Use `feat` for a new feature and `fix` for a bug fix; other appropriate types such as `docs`, `refactor`, `test`, `build`, or `chore` are allowed. Scope is optional and should name a real area of the reviewed changes. Add `!` immediately before `:` or a `BREAKING CHANGE: ...` footer only for a genuine breaking change.
- Describe the reviewed changes, not the work session. Keep the subject short and specific; add a blank line before an optional body, and a blank line before optional footers. Do not claim tests passed or an issue was fixed unless the evidence supports it. If reviewed changes contain unrelated work, recommend splitting commits rather than squeezing them into a misleading summary.
- For self-application, the user can stage the intended changes with `git add` if needed, then copy the message into `git commit` (or run `git commit -m 'subject'` for a simple single-line subject); Git commits only staged changes. Avoid suggesting an unsafe shell command when the message contains quotes or shell-special characters. For an agent-applied commit, require explicit approval of the proposed message and verify the staged scope matches the reviewed changes first; if scope changes, return to step 1.
